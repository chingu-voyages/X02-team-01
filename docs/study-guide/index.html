02The pantry: how questions are stored

Story A question is a folder. Each rewrite is a page inside the folder. Only one page may be marked live at a time. The folder remembers the certification, category, and difficulty; the page remembers the wording, the options, the review result, and whether it is published. The answer key sits in a separate locked drawer.
Pro track Seven tables. questions holds stable identity; question_versions holds editable content. The composite FK (certification_id, category_id) → categories(certification_id, id) makes it impossible to attach a category from a different certification.
Deep dive Versioning lets an editor fix a typo without destroying exam history. A partial unique index enforces at most one active version per question; a CHECK enforces active ⇒ approved. Answer keys live in child tables, so they can be omitted from the learner-facing query by construction.
DB-enforced
One active version per question · active requires approved · composite category/certification FK · non-blank text · one correct-option position per version · no cascading deletes.
Service-enforced
A multiple-choice version needs ≥ 2 options and ≥ 1 correct option. Single-select needs exactly 1 correct. Short-answer needs exactly 1 key row. These span rows, so a database CHECK cannot express them.
Never in GET
answer_options.is_correct and text_answer_keys.expected_answer are never in the pre-submission response. Review details, publication state, and is_flagged are also omitted.

03The version story: safe edits without losing history

Story Imagine a question folder. You write page 1. It gets checked and becomes the live page. Later you want clearer wording, so you write page 2. Page 1 stays in the folder as history. Only one page can wear the green LIVE badge. When page 2 is approved, it takes the badge; page 1 becomes historical. Nothing is silently overwritten.
Question identity
certification, category, difficulty, author
has
Version 1
draft → pending → approved → active
edit
Version 2
draft / pending / approved

One live version

Two independent switches

SwitchValuesMeaning
review_statuspending, approved, rejectedHas an editor checked it?
publication_statusdraft, active, retiredIs it visible to learners?
is_flaggedtrue / falseEmergency brake for bad content.
Pro track Eligibility is the AND of three conditions: review_status = 'approved', publication_status = 'active', is_flagged = false. Pending, rejected, draft, retired, and flagged versions are excluded at the repository.

What the database guarantees

  • UNIQUE (question_id, version_number)
  • UNIQUE (question_id) WHERE publication_status = 'active'
  • publication_status != 'active' OR review_status = 'approved'
  • review_status = 'pending' OR (reviewed_by_id IS NOT NULL AND reviewed_at IS NOT NULL)
  • version_number > 0 and non-blank text
  • All foreign keys are NO ACTION; no CASCADE
Gotcha The unique active-version index is partial: it only applies to rows where publication_status = 'active'. Drafts and retired versions can coexist freely.

Deep dive Review and publication are separate because an editor's approval and a release decision are different jobs. A question can be approved but still draft (not released), and it can be retired without deleting its history. The flag is the emergency brake: it hides a version without changing its review or publication record.

05One request, step by step

Story You show your wristband at the door. The waiter checks it, walks to the pantry, asks only for food that is approved, live, and not recalled, plates it, and removes the secret answer sauce. If the wristband is missing or fake, the door stays closed with a 401.
curl / browser
Authorization: Bearer <jwt>
FastAPI
route + dependencies
auth
decode + subject
repository
eligibility query
PostgreSQL
rows + options + keys
  1. Request arrives. The client calls GET /api/v1/questions with an Authorization: Bearer <token> header.
  2. Extract the credential. HTTPBearer(auto_error=False) returns None if the header is missing, so the dependency can produce a clean 401 instead of a framework default.
  3. Verify the wristband. decode_access_token checks the HS256 signature and the required sub, iat, and exp claims. Invalid or expired tokens raise 401 with WWW-Authenticate: Bearer.
  4. Build the repository. get_question_repository receives a Session from get_session and returns SQLModelQuestionRepository(session).
  5. Filter in SQL. The repository selects only versions where review is approved, publication is active, and is_flagged is false.
  6. Load the pieces. It loads each parent question's difficulty, the options ordered by position, and the short-answer key. It maps rows to frozen domain objects.
  7. Remove the answer key. The service maps each domain object to QuestionOut / QuestionOptionOut. Those models have no is_correct or expected_answer field, so the secret cannot leak even if a future developer adds it to the domain object.
  8. Serialize. FastAPI returns {"items": [...], "count": N}. An empty bank is a successful 200, not an error.
the eligibility filter (SQL idea)
WHERE review_status = 'approved'
  AND publication_status = 'active'
  AND is_flagged = false
the response contract
{
  "items": [
    {
      "id": "v-1004",
      "question_text": "Which Scrum event is 15 minutes?",
      "question_type": "multiple_choice",
      "allows_multiple_answers": false,
      "difficulty": "easy",
      "options": [
        {"position": 1, "option_text": "Daily Scrum"},
        {"position": 2, "option_text": "Sprint Review"}
      ]
    }
  ],
  "count": 1
}
Gotcha The repository does load is_correct and expected_answer so a future grading endpoint can use them. The service is the firewall. Never return the domain object directly.
200
Eligible questions, or an empty list. The count is the list length.
401
Authentication required when the header is absent; Invalid or expired authentication token when verification fails.
422
FastAPI validation error for a malformed request. The GET has no body, so this is mostly a safety net.

backend/app/repositories/sqlmodel_repository.py · excerpt
The real worker. It filters in SQL, then loads parents, options, and text keys in three follow-up queries to avoid a row explosion.
def list_eligible(self) -> list[Question]:
    versions = self._session.exec(
        select(QuestionVersion)
        .where(
            QuestionVersion.review_status == "approved",
            QuestionVersion.publication_status == "active",
            QuestionVersion.is_flagged.is_(False),
        )
        .order_by(QuestionVersion.question_id,
                  QuestionVersion.version_number)
    ).all()
    if not versions:
        return []

    version_ids = [v.id for v in versions]
    question_ids = {v.question_id for v in versions}

    questions = {
        q.id: q for q in self._session.exec(
            select(QuestionModel).where(
                QuestionModel.id.in_(question_ids))
        ).all()
    }

    options: dict[UUID, list[QuestionOption]] = defaultdict(list)
    for option in self._session.exec(
        select(AnswerOption)
        .where(AnswerOption.question_version_id.in_(version_ids))
        .order_by(AnswerOption.question_version_id,
                  AnswerOption.position)
    ).all():
        options[option.question_version_id].append(
            QuestionOption(option.position, option.option_text,
                           option.is_correct))

    expected_answers = {
        key.question_version_id: key.expected_answer
        for key in self._session.exec(
            select(TextAnswerKey).where(
                TextAnswerKey.question_version_id.in_(version_ids))
        ).all()
    }

    return [Question(...) for version in versions]
backend/app/repositories/in_memory.py · excerpt
The rehearsal worker. The same predicate, no database.
def _is_eligible(question: Question) -> bool:
    return (
        question.review_status == "approved"
        and question.publication_status == "active"
        and not question.is_flagged
    )
Gotcha The domain object intentionally carries is_correct and expected_answer. That is safe only because the service maps to response models that omit them. If someone changes the endpoint to response_model=Question, the answer key leaks.
Why three queries, not one join? A join across versions and options multiplies rows: three options turn one version into three rows, and nested keys make it worse. Loading versions, then options, then keys keeps the shape predictable and avoids duplicate-question bugs.

08Code atlas 3: service, contract, endpoint, auth

The firewall The service is where the secret sauce is removed. The response schema is the second lock: even if a field survives the mapping, Pydantic drops anything not declared on the model.
backend/app/services/question_service.py · excerpt
Map domain to contract. The response model has no answer fields, so this is a structural guarantee, not a manual delete.
def get_eligible_questions(repo: QuestionRepository) -> QuestionList:
    items = [_to_out(q) for q in repo.list_eligible()]
    return QuestionList(items=items, count=len(items))

def _to_out(question: Question) -> QuestionOut:
    return QuestionOut(
        id=question.id,
        question_text=question.question_text,
        question_type=question.question_type,
        allows_multiple_answers=question.allows_multiple_answers,
        difficulty=question.difficulty,
        options=[_option_to_out(o) for o in question.options],
    )

def _option_to_out(option: QuestionOption) -> QuestionOptionOut:
    return QuestionOptionOut(
        position=option.position,
        option_text=option.option_text,
    )

backend/app/api/deps.py · excerpt
The wristband check. Missing credentials and invalid tokens both become a clean 401.
bearer_scheme = HTTPBearer(auto_error=False)

def get_current_subject(credentials: Annotated[
    HTTPAuthorizationCredentials | None,
    Depends(bearer_scheme),
]) -> str:
    if credentials is None:
        raise HTTPException(401, "Authentication required",
                            headers={"WWW-Authenticate": "Bearer"})
    try:
        subject = decode_access_token(credentials.credentials)
        if not subject:
            raise jwt.InvalidTokenError("Missing subject")
        return subject
    except jwt.InvalidTokenError as exc:
        raise HTTPException(401, "Invalid or expired token",
                            headers={"WWW-Authenticate": "Bearer"}) from exc
